# Refactoring Review Criteria

Read this reference when changing routers, normalization boundaries, mixed coordinators, stateful adapters, utility collections, or module entry points. Select checks relevant to the actual change; these are engineering acceptance criteria, not universal React/TypeScript mandates or a required folder template.

## Responsibility Boundaries

- For every mixed file, record stable group/finding IDs, its logical groups, inputs, outputs, dependencies, effects, and reasons to change. Name concrete policies and their consumers. A broad architectural label does not establish a shared reason to change.
- Give each discovered independent policy a cohesive owner within the authorized refactoring scope. Keep the coordinator focused on ordering/composition, migrate callers, and remove the superseded implementation. A helper extraction that leaves independent policies under the same mixed owner does not close the finding. Any unresolved group keeps architecture incomplete; identify the exact constraint rather than silently excluding it.
- Identify parsing/validation, representation mapping, orchestration, resource ownership, concrete effects, and compatibility dispatch in the target. Separate responsibilities that change independently. Keep related rules together; one function or file per branch is not a goal.
- A routing coordinator should make precedence and terminal outcomes visible. It should not also decode embedded JSON, construct legacy UI-handler contexts, normalize identifiers, and mutate unrelated state. Move those responsibilities to their actual owners rather than wrapping the original body in more functions.
- Define boundary contracts around the operations the scenario needs. An opaque generic carrying an entire hook registry or framework context does not establish a meaningful application boundary. Concrete adapters own that context and translate it explicitly.
- Keep representation types with their model and integration contracts with their boundary. Separate them from orchestration when they have independent consumers and reasons to change. Do not create an unrelated shared-types dump or mirror every class with an interface.
- Choose a simple switch, an ordered dispatch chain, composition, or a stateful object based on the problem. Preserve protocol precedence and receiver binding. A thin adapter can be justified by binding, snapshot ownership, validation, or translation; its small size alone is not grounds for deletion.

## Layer Boundaries and Dependency Direction

Identify roles from behavior, contracts, consumers, and resource ownership before applying these constraints. These are dependency rules, not a required directory template; a small module may not need every role.

| Role | Allowed dependencies | Boundary violations to resolve |
| --- | --- | --- |
| Domain rules and values | Domain concepts and framework-independent primitives | SQL/ORM clients or entities, transport clients, React/hooks, concrete application stores, DOM/storage APIs, and driver-specific types or errors. |
| Application scenarios | Domain rules and narrow ports owned by the scenario or its inner contract owner | Concrete persistence/network/store implementations, UI component contracts, and SDK/ORM objects leaking into scenario inputs or results. |
| External adapters, including persistence and framework UI | Inner contracts plus the external mechanism they adapt; explicit data/error translation | Business policy hidden in driver/framework wiring, or an inner consumer importing its required port from the concrete adapter. |
| Composition | Inner operations and concrete adapters needed to assemble them | Business decisions or hidden resource startup disguised as dependency registration. |

For actual I/O boundaries, define a port in terms of the consumer's operations and domain values. A function contract can be sufficient; do not add a repository interface or DI container for every class. The concrete adapter depends on the port, and the composition boundary supplies it to the consumer. Trace the real import direction: passing a concrete ORM client through a constructor does not make the application independent of that ORM.

Keep database rows, ORM entities, vendor DTOs, SDK exceptions, and React/store objects outside business contracts when they carry external representation or lifecycle assumptions. Translate at the adapter boundary. Reuse genuinely independent value contracts where their semantics match instead of creating duplicate DTOs merely to populate layers. Preserve identifier precision, field presence, error causes, and required effects through any translation.

Inspect reachable helpers, imports/re-exports, callbacks, and type dependencies for transitive leaks. Verify business rules/scenarios using data and suitable in-memory port implementations without starting a real database, network, browser, or React renderer. Assert observable results and state; mocks or passing tests alone do not prove import independence. Use existing lint/dependency tooling where practical, scoped to the affected boundary, and record evidenced exceptions or unresolved edges in the existing responsibility map.

A React component, Hook, or provider can legitimately own UI lifecycle and import React. A persistence adapter can legitimately import its driver. Do not classify either as business logic solely from its filename, nor move framework-owned responsibilities into a pure layer to satisfy a folder convention. Distinguish these valid dependencies from actual policy leaks in the final architecture verdict.

## Abstractions, Helpers, and Entry Points

- **Class, value object, function, or DTO:** explicitly evaluate an invariant-owning value object or stateful class where valid construction, identity, legal transitions, or resource lifetime need a single owner. State which invariants or transitions it protects and how callers use it. Choose pure functions for stateless policy/transformations and plain contracts for data transfer when object ownership adds no benefit. A class made only of static wrappers does not resolve a mixed responsibility; function count and file size do not decide the form.
- **Helper disposition:** inspect exported and private policy helpers and forwarding chains, their callers, side effects, and actual policy. Keep shared guards, precedence rules, precision-preserving parsing, and canonical representation logic when they serve a real contract. Consolidate duplicated rules under their owner; inline or delete trivial forwarding without a responsibility when safe, and migrate callers. Do not delete a small function just because it is short, or preserve one merely because a caller exists. Record what value remains after removing the indirection.
- **Utility ownership:** broadly named utility modules must pass the same responsibility map as any other module. Identify each concept's owner and consumers. Do not move domain rules into a miscellaneous collection to make another file smaller. Shared validation primitives can be cohesive; representation conversion, transition policy, and integration effects require separate ownership analysis when their reasons to change differ. A filename alone neither proves nor disproves cohesion.
- **Public entry point versus relay:** evaluate each re-export-only file against direct imports from the actual owners. Retain it only for an evidenced responsibility, such as a published package path, an explicit supported API requirement, a necessary build/runtime boundary, or deliberate encapsulation enforced for its consumers. Existing imports, a curated list, a facade comment, or a linter rule preserving an otherwise unnecessary hop do not establish that responsibility. State what would be lost beyond mechanical import rewrites; do not invent compatibility requirements from current usage. Without such evidence, migrate in-scope consumers and remove the relay. Preserve explicitly required public paths. Check import evaluation and side effects before rewiring, and avoid exposing extra helpers merely to fill a barrel.
- **Construction and parsing:** related factories, constructors, parsers, and serializers must use an explicit shared validity/canonicalization policy. Verify semantic round trips for accepted values and consistent handling of invalid, boundary, and precision-sensitive inputs. If a factory successfully returns a domain value that its paired parser rejects, resolve the mismatch or identify an evidenced caller-owned precondition; do not claim the invariant is encapsulated. Type aliases, assertions, or renaming a formatter into a constructor do not enforce validity. Preserve established wire acceptance unless a behavior change is authorized and documented.

Use the existing Engineering Decision records to explain these choices, with consumer/invariant evidence and cleanup outcomes. In the final review, identify removed helpers/proxies, justified retained entry points and aliases, selected object/function ownership, and unresolved invariant gaps. An unexplained abstraction or public relay remains an open structural finding.

## Mandatory Residual Symbol Review

At discovery, identify all utility collections, coordinators, adapters, and entry points in the authorized inventory. Include unchanged files and files explicitly questioned by the user; do not limit this review to the diff or to modules already declared mixed. Treat broad names such as `utils`, `values`, `common`, `helpers`, or `events` as discovery cues, not automatic defects. Enumerate their module-level declarations, private policy helpers, policy-bearing methods, aliases, bound exports, and re-exports from the code. Read their bodies and reachable helpers before assigning a disposition.

Keep a compact symbol disposition table in the existing module report; do not create a second reporting system. Every candidate needs its actual consumer or reachability evidence, semantic owner, relevant invariant/effect, action (`keep`, `inline`, `consolidate`, `relocate`, or `remove`), and implementation or retention evidence. Symbols may share a row only when listed explicitly and governed by the same ownership rule; "all remaining helpers reviewed" is not a disposition. Missing entries remain unreviewed. Reuse unchanged entries on resume when their inputs still match.

For each candidate, compare the retained abstraction with the simpler alternative of direct access, inlining, or an existing owner. Identify the contract, invariant, ownership, or isolation that alternative would lose. A current caller establishes reachability, not necessity. Bound exports can protect a private instance and receiver; wrappers can adapt an actual boundary. Demonstrate that role rather than retain or delete them by shape alone.

- **Utility cohesion:** name the shared semantic rule for every retained group. Reject "all pure", "all scalar", "all protocol", or "all presentation" as sufficient explanations. Separate independently changing identity, numeric validity, representation, and domain-default policies when inspection establishes different owners. Shared low-level guards may remain together if they serve one evidenced validation contract. Preserve differences in accepted inputs and absent/undefined/null results; neither merge validators by similar bodies nor scatter every guard into its own file.
- **Coordinator residue:** distinguish dependency assembly and effect ordering from context acquisition, source precedence, fallback rules, decoding, and business policy. Those policies need explicit owners when they change independently. Extracting a private helper inside the same mixed coordinator does not close that finding. Snapshot acquisition that reads stores, registries, or clocks belongs at an integration boundary; a pure transformation may consume its explicit data. Do not move effectful context acquisition into a pure layer merely because its name matches that layer. Record snapshot timing and preserve it across extraction.
- **Protocol cohesion:** distinguish envelope metadata, message classification, command correlation, failure interpretation, and domain-state decoding. Sharing one transport does not prove one reason to change. Group by actual contracts and consumers, retaining related parsing together when justified; do not impose one file per message or branch.
- **Relay cleanup:** compare every entry point and forwarding chain with the public-boundary criteria above. Migrate consumers and remove unnecessary hops now within the authorized scope. Changing an internal import is part of refactoring; an explicitly supported public API or real external constraint must be preserved or recorded as an unresolved dependency.

At closure, reconcile the symbol table with both retained originals and destinations. A file count, graph scan, passing tests, or a file-level "reviewed" flag cannot substitute for this review. Challenge every `keep`: if its rationale could justify any unrelated collection or relay, it is too generic. Implement feasible cleanup and reopen unsupported closures; any unresolved candidate or independently changing policy keeps architecture unverified. This gate improves review accountability; it is not an automated proof of cohesion.

## Transitive Effect Review

Follow the helper calls reachable from each mapped group, including injected callbacks and cache/store adapters. Record each observable mutation, persistence operation, subscription, or other external action and its call path. Review helper implementations rather than infer purity from names or return types. A formatting function that calls a helper which writes a cache is effectful even when its own body contains no write.

Separate pure presentation policy from required cache/state changes at an explicit effect-owning boundary. Preserve effect timing, data, and failure behavior unless a change is authorized. Verify both returned data and resulting cache/state; deleting a required write to make a formatter pure is a behavioral regression. An uninspected dynamic helper remains a stated evidence gap.

## Behavioral Checks Across Boundaries

| Changed area | Evidence to obtain |
| --- | --- |
| Decoder, mapper, object merge | Preserve missing fields separately from `undefined` and `null`, identifier precision, unknown wire fields, and documented metadata precedence. Test the actual decoder-to-consumer path, including metadata present only inside a payload. Do not tighten an accepted input format without contract evidence and an explicit behavior change. |
| Domain construction or representation conversion | Compare factory/constructor acceptance with parser/serializer acceptance and documented canonicalization. Exercise semantic round trips, invalid inputs, bounds, and identifier precision through actual consumers. Record required caller preconditions and authorized changes; a successful construction must not silently promise validity that the paired parser rejects. |
| Dispatch pipeline | Exercise overlapping matches, first-owner termination, unknown/malformed input, and handler registration changes. If dispatch uses a mutable registry, define whether one frame uses one snapshot and test that policy. Preserve differences between top-level and nested payloads. |
| Deferred state reconciliation | Identify which values must be captured with their owner and which must be read fresh. Test a newer explicit user choice within the same scope, rapid scope changes, and cancellation. An identity check alone does not protect newly changed state inside an unchanged scope. |
| Subscription or projection | Test startup with prepopulated state, updates around setup, and stop/start or replacement. Define initial reconciliation, not only future-event handling; test that stale cleanup cannot release the current owner's resource. |
| Error conversion or cleanup | Identify expected failures for each catch. Preserve unexpected error causes through a diagnostics boundary or propagate them according to the contract. Test partial setup and cleanup failures where they can leave resources or pending state behind. |

Assert consumer-visible data and final state, not only helper calls, branch counts, or the existence of new files. Test doubles should implement the real port contract without unchecked casts that hide mismatches. Do not write redundant tests for mechanical moves.

## Final Review

Apply the whole-folder consolidation review below before assigning the architecture verdict; a complete symbol table alone is insufficient.

Reconcile every group/finding ID with its final owner, affected callers, and closure evidence. Inspect the bodies at their final locations; changes in names or file count do not establish separation. Assess cohesion, dependency direction, transitive effects, and remaining mixed modules independently of test results.

Re-review the remaining original files after extraction as well as their destinations. Record whether each remaining group has a cohesive owner, needs further separation, or is a justified composition boundary. Keep unresolved residual work in the same finding ledger; do not declare extraction itself the endpoint.

Record separate behavior and architecture verdicts. Behavior can be verified while architecture is incomplete. Architecture cannot be verified with an unresolved in-scope mixing finding, an unreviewed effect path, or a policy merely relocated into another generic projection module. A positive verdict must identify what changed and why each remaining coordinator is cohesive.

For affected similar contracts, record the duplicates eliminated and the reasons for each retained separation under the skill's Contract Identity and Reuse criteria. Check actual consumer semantics and field-presence behavior; matching fields or different type names alone do not establish whether concepts should be shared.

Compare the final responsibility map with the original problem. Search for old symbols and reachable superseded paths, and apply the skill's Legacy Cleanup rules to intentional compatibility code. Check relocated bodies as carefully as new code. Where a stable local boundary can be enforced by an existing linter or dependency check, add and verify that check; avoid arbitrary line-count limits or tests that merely match implementation text. Report concrete remaining defects or uncertainty; do not use passing checks to waive an unresolved finding. Persist the evidence and remaining dependencies using [migration-reporting.md](migration-reporting.md); a verified folder refactor does not establish migration-wide completion.

## Whole-Folder Consolidation Review

Review the final production tree, module bodies, and dependency/data flow before consulting the completion checklist or accepting earlier verdicts. Cover the full authorized folder, not just edited files or previously reported problems. Explain how a maintainer follows one operation from entry to outcome and finds the owner of each independently changing rule.

- **Layout and placement:** every module/group must have a concrete semantic role and consistent allowed dependencies. Classify a transformation by its actual input/output/effects; its name, the presence of a `project` verb, or the number of functions does not determine placement. Identify duplicated ownership, mixed abstraction levels, and policies stranded in unrelated folders. Resolve inconsistencies rather than merely rename the surrounding directory.
- **Fragmentation:** examine new and retained tiny modules, one-function files, forwarding paths, and repeated cross-file navigation. Compare each with local functions or consolidation under an existing cohesive owner. A reusable invariant justifies centralizing a rule; it does not by itself justify a separate file. Distinct validators can retain different acceptance/presence contracts inside one cohesive module. Retain a separate module for a concrete responsibility-boundary or navigation benefit, such as a stable policy boundary, substantial independently maintained transformation, resource owner, or required entry point. Several callers, different primitive data categories, or a dedicated filename alone do not establish that benefit. Do not enforce a minimum function count, merge unrelated policies to reduce file count, or require one file per responsibility.
- **Coordinator integrity:** list what each retained coordinator still decides, not only what was extracted. Separate independently changing source selection, fallback, decoding, and presentation policy from dependency assembly and effect ordering. A shared operation or required call sequence does not by itself justify housing every participating policy in the coordinator. Give each remaining policy a specific owner and compare the simpler alternative; grouping all symbols under one `keep` cannot replace that decision.
- **Change scenarios:** trace representative independent changes through the chosen layout. State which owners should change and why unrelated rules remain isolated. Conversely, show that a cohesive change does not require unrelated leaf files or needless forwarding hops. Use inspected contracts and call paths rather than speculative application features.

Reconcile this review with the original whole-folder map and all new/inherited findings. Implement feasible consolidation and cleanup, then verify any affected behavior and wiring. Record concise layout decisions and unresolved constraints in the existing report. Architecture remains unverified when the map omits production files, known mixing persists, or fragmentation/placement concerns are left without specific evidence. Neither more files, fewer lines, unchanged policy bodies, nor a longer inventory proves architectural improvement.
